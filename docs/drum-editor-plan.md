# Плагин многомикрофонного анализа и монтажа ударных

Рабочий план: архитектура, алгоритмы, этапы.

---

## 1. Задача

Есть набор моно-стемов ударной установки — один микрофон = одна дорожка. Типичный набор: бочка внутри, бочка снаружи, снейр сверху, снейр снизу, хай-хэт, томы по одному на барабан, пара оверхэдов, один-два комнатных микрофона, иногда микрофон подбочника или «мусорный» перегруженный канал. Итого от 4 до 24 дорожек.

Инструмент должен:

1. Проанализировать все дорожки и найти удары.
2. Понять, какой барабан ударил.
3. Свести один и тот же удар между микрофонами по времени и фазе с субсэмплевой точностью.
4. Нарезать материал по ударам одинаково на всех дорожках.
5. Дать редактировать результат: сдвигать, квантовать, выравнивать динамику, править ошибки анализа руками.

## 2. Архитектурное решение: свой документ, DAW delivery — отдельный слой

Обычный VST3/AU видит только поток сэмплов блоками и не имеет доступа ни к таймлайну, ни к соседним дорожкам. Резать и двигать он не может в принципе. Выходов два, и они не исключают друг друга.

**ARA 2** (Audio Random Access, SDK Celemony, открыт на GitHub, поддержка встроена в JUCE, есть `ARAPluginDemo`) даёт доступ ко всему аудиофайлу целиком и вне реального времени, знание позиций регионов на таймлайне, изменённое воспроизведение без правки исходников и — главное — **общий документ между инстансами**: инстанс на снейре видит аудио инстанса на бочке. Прецеденты: Melodyne, VocAlign, SpectraLayers, Sound Radix Auto-Align Post 2. Хосты: Studio One, Reaper, Logic, Cubase/Nuendo, Cakewalk, Samplitude. Ableton Live — нет.

**Свой standalone-редактор** — приложение поверх стемов: файлы свои, таймлайн свой, документ один по определению, координатор сессии не нужен. Результат уходит в DAW стемами от общего нуля сессии.

**Решение: сначала standalone-редактор, DAW delivery — поверх той же машины.**
Ближайший delivery-канал для MVP-хоста — Reaper `.RPP` export из standalone;
ARA остаётся вторым каналом, когда монтаж уже работает и нужен внутри хоста.

Почему в этом порядке:

- ARA не экономит ни строчки интерфейса. Стек волновых форм, маркеры, правка мышью, A/B из секции 7 пишутся одинаково в обоих случаях; ARA добавляет только доступ к аудио хоста. Интерфейс — основная стоимость этапа 2, и она общая.
- Всё, ради чего берут ARA — файл целиком, таймлайн, общий документ, — в своём приложении есть даром.
- ARA стоит дорого сразу: лицензирование SDK для коммерческого продукта не выяснено (секция 11), поведение отличается от хоста к хосту, отладка идёт через чужой процесс.
- Ошибиться в модели монтажа дешевле в своём приложении, чем в интеграции с шестью хостами.

Цена решения — трение процесса: стемы обязаны быть экспортированы от одного нуля сессии, а круг «экспорт → выравнивание → импорт» инженер проходит руками. Это трение рабочего процесса, а не потолок качества: Auto-Align Post 2 продавался в такой модели годами.

**Условие, без которого решение становится тупиком.** Модель документа — источники, события, поле задержек, регионы, решения выравнивания — живёт отдельной библиотекой рядом с `beat_dsp` и не знает ни про окна, ни про приложение. Тогда RPP export и ARA-плагин становятся адаптерами хоста поверх той же модели. Если документ срастётся с оболочкой standalone, delivery-слой придётся начинать заново. Канон: `decisions/editor-in-standalone-ara-is-delivery.md`.

### Модель работы

Standalone-редактор:

- проект = один набор стемов одной установки, снятый в одну сессию;
- дорожки грузятся файлами, роли назначаются в той же таблице;
- анализ, события и решения общие для всех дорожек проекта;
- слушают через монитор-микс со своей панорамой и уровнем, а не через разводку «канал в одноимённый выход»;
- результат уходит наружу стемами и sidecar-файлом решений.

Плагин этапа 1 (VST3/AU, N-in/N-out) остаётся и живёт своей жизнью: статическое выравнивание в реальном времени полезно само по себе.

Reaper round-trip (этап 4) создаёт `.RPP` из standalone-экспорта и sidecar,
чтобы инженер мог вручную править regions/stretch markers в DAW. ARA, когда до
него дойдёт: инстанс на каждой дорожке, первый создаёт общий документ и
становится координатором сессии, в интерфейсе любого инстанса видны все
дорожки, каждый инстанс рендерит только свою.

### Режимы интерфейса

Интерфейс редактора делится на Basic и Advanced. Basic — стартовый режим с
минимальным набором действий и доверием к автоматике; Advanced — инженерный
стенд с ручками, диагностикой, source-centric таблицами и ручной правкой.
Оба режима смотрят на один документ и одни параметры, а не на разные
алгоритмы. Канон: `decisions/basic-advanced-ui-modes.md`.

Вводить режимы отдельной серией PR, не смешивая с DSP и нарезкой:

| PR | Фокус | Граница |
|---|---|---|
| 40 | Каркас: `global.uiMode`, переключатель в header, named visible-блоки и Basic по умолчанию | Только видимость существующих блоков; Advanced восстанавливает текущий экран |
| 41 | Таблица каналов под Basic/Advanced | Разные наборы колонок, без изменения параметров выравнивания |
| 42 | Basic outcome/status | Пользовательский итог и основные действия вместо инженерных строк |
| 43 | Advanced diagnostics v2 | Полная source-centric таблица, роли каналов, room/OH return как роль, а не просто `late Ch` |

### Обмен с DAW

| Формат | Что несёт | Когда |
|---|---|---|
| WAV-стемы от общего нуля | Результат целиком; импортирует любой хост | Есть (`Export aligned`) |
| Sidecar JSON рядом со стемами | Задержки, полярности, события, ручные правки, edit regions, stretch decisions | Вместе с редактором: без него проект не открыть повторно |
| MIDI из событий | Триггеры, замена, программирование | Секция 6.1 |
| RPP (Reaper) | Созданный проект с импортированными стемами, markers/regions, align decisions и stretch/edit decisions | После sidecar и стабильной модели edit regions: целевой хост MVP, формат текстовый |

**Reaper round-trip.** Так как целевой хост MVP — Reaper, standalone должен
уметь экспортировать не только WAV, но и готовый `.RPP`: создать проект,
разложить исходные или aligned-стемы от общего нуля, перенести маркеры событий,
regions, решения выравнивания и будущие stretch markers/разрезы настолько
нативно, насколько позволяет формат. Это не заменяет собственный документ:
sidecar остаётся источником правды, а RPP — удобный канал доставки для ручной
доработки инженером в DAW. Если Reaper-формат чего-то не несёт без потерь,
проект должен всё равно ссылаться на sidecar, а не превращаться во вторую
модель состояния.

AAF/OMF не брать: цена реализации несопоставима с выигрышем.

### Роли дорожек

Назначаются пользователем, детектируются автоматически как предположение:

| Роль | Поведение |
|---|---|
| Близкий микрофон (kick, snare, tom) | Источник событий: здесь ищутся удары |
| Пара оверхэдов | Ведомая, выравнивается; служит опорой для стереообраза |
| Комната / ambience | Ведомая, выравнивание опционально (иногда задержка — это художественный эффект) |
| Хай-хэт, райд | Промежуточная: может быть и источником, и ведомой |

## 3. Конвейер анализа

Как строить детектор, что заложить в `Event` с первого дня и **когда** звать
сеть (не раньше ступени 5 лестницы): `detector-design-recommendations.md`.
Спектральный поток ниже — ступень 1. Не начинать с RTNeural/ONNX.

Детектор отвечает «где примерно и что это». Отдельный вопрос — **где у этого
удара границы в каждом микрофоне**: что принадлежит ему, а что просачиванию,
хвосту предыдущего и шуму. Без ответа квантизация двигает не то, что нужно, и
смазывает атаку оверхеда. Канон: `hit-segmentation-recommendations.md`.

### 3.1 Детекция онсетов

- База: **positive spectral flux** с адаптивным медианным порогом и peak picking.
- Дополнительный признак: **HFC** (high frequency content), помогает по хай-хэту и тарелкам.
- Окно ~1024 сэмпла, хоп ~128–256 при 48 кГц.
- Отдельная полосовая ветка для низа (бочка, флор-том), где спектральный поток слабее и порог должен быть другим.

### 3.2 Подавление ложных срабатываний от просачивания

Главная проблема, а не пороги. Микрофон снейра слышит бочку и наберёт вдвое больше «ударов», чем было сыграно.

Решения:

- события ищутся только в дорожках с ролью «близкий микрофон»;
- **кросс-микрофонное голосование**: удар в пределах окна ~10 мс во всех каналах засчитывается тому, где онсет и раньше, и энергичнее относительно собственного среднего уровня;
- проверка на физическую задержку: если онсет в снейре опережает онсет в бочке на величину, невозможную при их расположении, это просачивание.

### 3.3 Классификация удара

Основной признак — **вектор энергий по всем микрофонам** в окне вокруг онсета, нормированный. Он различает kick / snare / tom-N / hats / ride / crash надёжнее, чем спектр одного канала, и не требует обучения.

Дополнительно (после плато классики — ступени 2–4 лестницы, сеть не первая):

- римшот против обычного удара;
- гост-ноты;
- флэмы и раскаты как составные события;
- сдвоенный удар бочки.

Сначала: энергетический вектор, калибровка сессии, «найти похожие» по правкам.
Узкая модель (RTNeural/ONNX) — ступень 5, только классификация уже найденного
события, и только при замороженном тесте. Признаки: спектральный центроид, спад,
MFCC, форма атаки, энергетический вектор.

### 3.4 Уточнение позиции до долей сэмпла

Детектор онсетов даёт миллисекунды. Для фазы нужны доли сэмпла.

Второй проход: **GCC-PHAT** (обобщённая взаимная корреляция с фазовым взвешиванием) между опорным микрофоном удара и каждым остальным, в окне вокруг события. PHAT устойчив к тому, что один и тот же удар в разных микрофонах спектрально совершенно разный. Положение пика уточняется **параболической интерполяцией** по трём отсчётам.

## 4. Выравнивание

### 4.1 Полярность

Отрицательный пик корреляции = переворот фазы. Нижний микрофон снейра — почти всегда. Определяется автоматически, отображается в интерфейсе, переопределяется вручную.

### 4.2 Ограничение окна поиска

Задержка ограничивается физически возможной, исходя из заданного максимального расстояния между микрофонами (по умолчанию ~4 м ≈ 12 мс). **Без этого корреляция залипнет на соседний период низкочастотной волны** и выровняет всё в никуда. Это самая частая причина, по которой такие алгоритмы «иногда сходят с ума».

### 4.3 Дробная задержка

Целыми сэмплами фазу бочки не свести. Варианты:

- интерполяция Лагранжа (3–5 порядок) — дёшево, годится для realtime;
- олпасс Тирана — лучше по фазе, но нужен контроль устойчивости при смене коэффициентов;
- поворот фазы в частотной области — для офлайн-рендера точнее всего.

Поскольку основной режим офлайновый, разумно использовать частотный вариант для рендера и Лагранжа для превью.

### 4.4 Ключевое: выравнивание по-ударное

**Одной задержкой на канал задача не решается.** До оверхэда от бочки и от райда разное расстояние, поэтому оптимальный сдвиг оверхэда зависит от того, что сейчас звучит.

Отсюда:

- для каждого типа удара считается свой набор задержек по каналам;
- значения усредняются по всем ударам этого типа (медиана, чтобы выбросы не тянули);
- между значениями плавный переход на границах нарезанных фрагментов.

Это и есть настоящая причина резать, а не просто удобство монтажа.

### 4.5 Остаточная фаза

После временного выравнивания остаётся частотно-зависимое расхождение. Олпасс-ротатор в духе Little Labs IBP, один-два каскада с регулируемой частотой. Метрика для оптимизации и для индикатора в интерфейсе — **когерентность суммы**: максимум корреляции либо минимум гребёнчатости спектра суммы относительно спектров слагаемых.

### 4.6 Возврат естественной задержки комнаты и оверхедов

Оверхеды и комнатные микрофоны отстают от близких не случайно: это время
пробега звука, и именно оно даёт глубину и естественную реверберацию
помещения. Выровняв их полностью, инструмент выигрывает когерентность на
транзиенте и **теряет объём**: комната приходит одновременно с прямым звуком и
из пространства превращается в гребёнку.

Поэтому выравнивание обязано быть обратимым по каналу. Хранятся два числа:

- `d[i]` — сырой TDOA относительно опоры (уже есть в `ChannelEstimate`);
- `applied[i] = max(d) − d[i]` — то, что уходит в линию задержки.

Возврат задаётся долей `r[i]` ∈ [0…1]: сколько естественной задержки канала
вернуть обратно.

```
applied'[i] = max(d) − (1 − r[i]) · d[i]
```

`r = 0` — полное выравнивание, `r = 1` — исходная расстановка. Свойства,
которые делают это дешёвым:

- `applied'[i] ≥ 0` при любом `r` ∈ [0…1] — канал по-прежнему только
  задерживается, никогда не двигается вперёд (`AGENTS.md`, инвариант 2);
- `applied'[i] ≤ max(d)`, значит латентность не растёт и модель PDC не меняется;
- ничего не нужно переизмерять: возврат — это интерполяция между выровненным
  и исходным состоянием.

Значение по умолчанию — по роли (близкий 0, оверхеды и комната ближе к 1), но
как **подсказка**, а не автоматика: роли в этапе 1 метаданные (инвариант 8), и
сколько объёма оставить — решение инженера, а не алгоритма.

**Что из этого следует для этапа 2.** По-ударное выравнивание обязано считать
возврат по каждому удару отдельно, иначе комната «дышит» вслед за
барабанщиком. И карта деформации для комнатного канала должна быть более
пологой, чем для близкого: хвост реверберации — не удар, растягивать его вслед
за прямым звуком значит менять слышимый размер помещения. Канон растяжения —
`timing-design-recommendations.md`.

Решение: `decisions/room-delay-is-returned-not-removed.md`. Реализация — этап 2,
сейчас зафиксировано, чтобы формат состояния и по-ударное выравнивание не
построились на допущении «всё приходит одновременно».

## 5. Нарезка

- **Инвариант: все микрофоны режутся строго по одним и тем же точкам таймлайна.** Иначе вся фазовая работа рассыпается. Групповое редактирование не опция, а свойство модели данных: событие одно, у него один набор границ.
- Точка реза — ближайший переход через ноль с преролом несколько миллисекунд до атаки.
- Кроссфейды: для коррелированного материала равномощные дают горб на стыке, по умолчанию **равноамплитудные**. Длина настраиваемая, по умолчанию 2–5 мс.
- Флэмы, раскаты и сдвоенные удары бочки двигаются **как единое событие**, иначе превращаются в один удар.

### Дырки и хвосты после сдвига

Классическая боль. Набор мер, выбирается пользователем:

- растягивание материала вместо сдвига для оверхэдов и комнаты (эластик);
- подклейка из комнатного микрофона;
- ограничение силы подтяжки (strength в процентах);
- запрет двигать событие дальше, чем на N мс.

## 6. Функциональность поверх ядра

Отсортировано по отношению пользы к трудозатратам.

### 6.1 Экспорт MIDI

Времена ударов + велосити + классификация → MIDI-файл или drag-and-drop в хост. Почти бесплатно, когда анализ уже сделан, и это одна из самых востребованных функций такого класса инструментов. Триггер сэмплов дальше — чужая забота, не надо встраивать свой сэмплер.

### 6.2 Выравнивание динамики по ударам

Не компрессор, а покомандная коррекция велосити каждого события к целевому уровню с регулируемой силой. Для неровной игры работает несравнимо лучше динамической обработки. Применяется одинаковым коэффициентом ко всем микрофонам, чтобы не поехал баланс.

### 6.3 Квантизация и грув

- Привязка к сетке с регулируемой силой.
- Определение темпа и сетки **по самой игре**, а не по хостовому темпу — записи под клик не всегда.
- Извлечение грува из сыгранного для применения к другим партиям.
- Сохранение свинга.

### 6.4 Подавление просачивания

Между ударами — не гейт, а мягкие огибающие усиления с регулируемой глубиной (полное молчание звучит неестественно).

Полноценное спектральное подавление по кросс-канальной ковариации (в духе того, что делал Drumatom) — отдельный большой проект, но потенциально **главный дифференциатор продукта**. Выносится в отдельную фазу, не в первую версию.

### 6.5 Прочее

- Замена/дублирование удара сэмплом с сохранением фазовых отношений.
- Автоматический баланс микрофонов по эталонному соотношению уровней.
- Обнаружение клиппинга и проблемных ударов.

## 7. Интерфейс

Ни один автоматический детектор не работает всегда. **Инструмент выживает ровно в той мере, в какой инженер может быстро исправить ошибку руками.**

Обязательный минимум:

- вертикальный стек волновых форм всех микрофонов с общей временной осью;
- маркеры событий с индикацией уверенности классификации;
- добавление, удаление, сдвиг маркера мышью; переназначение типа удара;
- фильтрация отображения по типу удара («показать только томы»);
- A/B прослушивание до и после;
- моно-сумма в один клик и коррелометр;
- отображение вычисленных задержек и полярностей по каналам, с ручным переопределением;
- индикатор когерентности суммы как основная метрика качества.

Отрисовка: JUCE, кэш пиков волновой формы на нескольких уровнях детализации, перерисовка только грязных областей. Волновая форма на 24 дорожки по часу — само по себе инженерная задача, закладывать время.

## 8. Технические решения

- **Анализ строго в отдельном потоке.** В `processBlock` ничего тяжелее чтения готовых значений.
- **Результаты анализа сохраняются в состояние плагина.** Переанализировать час многодорожечной записи при каждом открытии проекта никто не станет. Формат состояния — свой бинарный блоб с версионированием, не XML.
- Кэш анализа привязывается к идентификатору источника (путь плюс хэш содержимого; на этапе 4 — идентификатор аудиоисточника ARA).
- Корректная отдача латентности хосту в realtime-режиме превью.
- FFT: `juce::dsp::FFT` для начала; при нехватке скорости — pffft (BSD-подобная лицензия, без проблем для проприетарного продукта). FFTW не брать: GPL либо платная лицензия.
- Обработка при разных частотах дискретизации: все пороги и окна задаются в миллисекундах и герцах, не в сэмплах.
- Тесты: набор эталонных многомикрофонных записей + синтетические сигналы с заведомо известной задержкой, автоматическая проверка точности выравнивания в сэмплах.

### Хранение материала

Стенд этапа 1 держит клип в памяти целиком (`FilePlayer`) — для прогона это честно, для редактора нет. Сколько занимает float32 в памяти:

| Материал, 6 минут | 48 кГц | 96 кГц |
|---|---|---|
| 8 дорожек | 0.55 ГБ | 1.1 ГБ |
| 16 дорожек | 1.1 ГБ | 2.2 ГБ |
| 24 дорожки | 1.7 ГБ | 3.3 ГБ |

Порядок величины задаёт не длина песни, а произведение «дорожки × частота»: удвоение частоты исходника стоит ровно столько же, сколько удвоение числа микрофонов. Пятиминутный кит на 96 кГц уже выходит за разумный резидентный размер, и это ожидаемый материал, а не крайний случай.

Решение для этапа 2:

- **Источник читается с диска через memory-mapped reader** (`juce::MemoryMappedAudioFormatReader`; WAV/AIFF не распакованы, отображаются как есть). В памяти живут только окно воспроизведения и окно анализа. Кэш страниц операционной системы делает работу, которую иначе пришлось бы писать руками.
- **Пик-пирамида** (min/max по уровням 1:256 и 1:65536) считается один раз при загрузке и лежит рядом с проектом. Она нужна для отрисовки в любом случае, а весит меньше процента от материала.
- **Анализ не обязан идти на нативной частоте.** Пороги и полоса заданы в мс и Гц (`AGENTS.md`, инвариант 4), GCC-PHAT работает в ~100 Гц…8 кГц, поэтому окно 96 кГц децимируется до 48 кГц: вдвое дешевле FFT без потери точности в миллисекундах. Уточнение позиции остаётся субсэмплевым. Проверить на реальном материале до того, как закладывать.
- **Две ветки хранения не заводить.** Как только стриминг есть, путь «весь клип в памяти» из редактора убирается; в плагине этапа 1 его вообще нет.

## 9. Этапы

Это порядок снятия продуктовых рисков, а не календарь и не обещание набора
функций к дате. Каждый этап обязан закончиться целым пользовательским
сценарием на реальной сессии, а не только набором классов и кнопок.

Правила дорожной карты:

- наблюдения, автоматические решения и ручные правки хранятся раздельно;
- любой автоматический результат можно проверить, отменить и воспроизвести
  после повторного открытия проекта;
- новый рендер сначала доказывает пользу на одинаковом входе против предыдущего;
- delivery-канал переносит уже работающий документ, но не заводит свою модель;
- следующий этап не блокирует выпуск полезного результата предыдущего.

| Этап | Результат для пользователя | Главный риск, который закрывается |
|---|---|---|
| 1 | Статически выровнять многомикрофонный кит в хосте | Слышима ли польза базового DSP |
| 2 | Открыть стемы, проверить удары и экспортировать по-ударно выровненный результат | Можно ли доверять событиям и менять задержку без артефактов |
| 3 | Закончить музыкальный монтаж песни в standalone | Экономит ли общая карта времени ручную работу инженера |
| 4 | Передать тот же документ в Reaper, затем при спросе в ARA-хост | Не теряется ли результат на границе с DAW |
| 5 | Ослабить просачивание лучше безопасной gain-огибающей | Даёт ли спектральный метод выигрыш без потери атаки и тарелок |

### Этап 1 — Статическое выравнивание (MVP)

Обычный VST3 с несколькими входными шинами, без ARA и без нарезки. Определение полярности, одна задержка на канал, олпасс-ротатор, коррелометр.

Даёт слышимый результат на любом материале, проверяет ядро анализа на реальных записях, не требует ARA. Это уже самостоятельный продукт.

### Этап 2 — Редактор: события и по-ударное выравнивание

Standalone-редактор. Модель документа отдельной библиотекой, источники с диска и пик-кэш, детекция онсетов, классификация ударов, по-ударное выравнивание и glide, нарезка с кроссфейдами, интерфейс с волновыми формами и ручной правкой, монитор-микс, экспорт стемов и sidecar.

Порядок работ. Сначала измерение, потом машинерия: открытый вопрос «насколько по-ударное выравнивание слышимо лучше статического» (раздел 11) закрывается глазами по полю задержек, до того как написан хоть один сдвиг.

Gate качества перед нарезкой — не средняя когерентность всей суммы. Оценка
делается по источникам: close-пара прямого звука (например snare top / bottom),
его наблюдения в соседних микрофонах, и отдельный возврат естественной задержки
room/OH. Комнатный микрофон можно измерять, но нельзя считать, что лучший
результат — всегда совместить его в ноль с close-микрофонами.

| Шаг | Что | Почему в этом месте |
|---|---|---|
| 1 | `beat_doc`: источники, каналы, событие с происхождением, поле задержек, кэш признаков, журнал правок, защищённая зона. Плюс синтетический многоканальный дубль в тестах | Модель документа заводится до первой фичи этапа (ADR `editor-in-standalone-ara-is-delivery`), стенд с известными временами — до первой строчки детектора (`detector-design-recommendations.md` 1.9) |
| 2 | `IOnsetDetector` и `SpectralFluxDetector`: ступени 1–2 лестницы — широкополосная огибающая и 6–8 логарифмических полос | Даёт изолированные удары и перцептивную атаку. Меряется на синтетике в сэмплах, precision и recall — отдельными числами |
| 3 | Сверка по всем микрофонам: событие предсказывается по `d[i]`, уточняется GCC-PHAT, оценивается голосованием. Поле `d(событие, канал)` и маркеры на осциллограммах | Ступень 3. Здесь появляется то, чего нет у одноканальных инструментов, и здесь же видно, есть ли смысл в шаге 4 |
| 4 | Калибровка сессии: `SessionProfile` и первый проход `SessionCalibration` — уровни каналов, матрица задержек с разбросом, матрица просачивания | Ступень 2 лестницы (`detector-design-recommendations.md` 2.2). Без априорной задержки уточнение сверки уточнять нечего; профиль обязан уметь «не знаю», иначе ноль читается как «микрофоны рядом» |
| 5 | `beat_doc` в плагине: кнопка Detect, события в worker-потоке, маркеры на осциллограммах и на полосе обзора, по-ударная задержка колонкой | Первый шаг этапа, который видно глазами. До рендера надо своими глазами увидеть, насколько по-ударная задержка отличается от статической — иначе шаг 6 делается вслепую |
| 6 | `GlideRenderer`: slew-лимит на существующей задержке, source-centric диагностика и метрика когерентности на событие | `timing-design-recommendations.md` 6. Возможно, на этом всё и закончится, но решать это можно только по источникам, а не по общей сумме |
| 7 | Точки реза, кроссфейды и при необходимости WSOLA на затухании | Только если glide измеримо не хватило |
| 8 | Формат проекта: sidecar, Save/Open, relink и миграции | Результат должен пережить закрытие приложения и перенос исходников |
| 9 | Очередь проверки и ручная правка событий/решений с undo/redo | Ошибка автоматики не должна вынуждать к переанализу всей песни |
| 10 | Сквозной gate этапа 2 на разных реальных китах | Этап заканчивается воспроизводимым рабочим процессом, а не demo-path |

Ступени 4–5 лестницы детектора (NMF на шаблонах сессии, обученная модель) в этот порядок не входят: до них нужен замороженный тестовый набор и доказанное плато классических методов.

Декомпозиция шага 7 после PR #46:

| Порядок | PR | Граница |
|---|---|---|
| 7.1 | Adapter `EditRegionPlan -> CrossfadeRenderer::EditPoint` | Только мост документа к DSP и синтетический/GUI-smoke; без новой кнопки и без WSOLA |
| 7.2 | Standalone `Export crossfade...` | Отдельный export path, статус и тест; не заменять `Export static...` и `Export glide...` |
| 7.3 | YAN9 gate для crossfade | Протокол чисел и слуховой smoke; без подгонки порогов под один кит |
| 7.4 | Decision model `glide / crossfade / WSOLA-needed` | Только расчёт и Advanced diagnostics; ручное переопределение позже |
| 7.5 | WSOLA primitive в `beat_dsp` | Синтетика: `strength = 0`, атака не меняется, small stretch/compress без дыр |
| 7.6 | WSOLA на `EditRegion.body` | Offline render по decay regions; crossfade остаётся join-слоем |

Наличие всех трёх путей `glide / crossfade / WSOLA` не является gate само по
себе. Если более простой рендер проходит измерение и слуховую проверку, этап не
надо задерживать ради более сложного алгоритма.

Декомпозиция продуктового завершения этапа 2:

| Порядок | Срез | Граница |
|---|---|---|
| 8.1 | Sidecar schema v1 | Источники, fingerprints, события, признаки, delays, edit regions, decisions, ручные правки и версия схемы; без JUCE и RPP |
| 8.2 | Save/Open проекта | Атомарная запись, явные dirty/error states, повторный рендер без переанализа |
| 8.3 | Relink sources | Поиск перемещённых файлов по fingerprint; несовпадение не принимается молча |
| 8.4 | Миграции | Fixture минимум предыдущей версии схемы и отказ с понятной причиной для неподдерживаемой |
| 9.1 | Review queue | Переход по low-confidence и конфликтным событиям, loop/audition, фильтр по источнику и типу |
| 9.2 | Правка события | Добавить, сдвинуть, переназначить тип; «ошибка детектора» и «не трогать» остаются разными действиями |
| 9.3 | Правка рендера | Per-event override автоматического решения и явный lock для повторного анализа |
| 9.4 | Undo/redo | Журнал команд документа, а не копии состояния в UI |

**Gate этапа 2:** один и тот же проект после Save/Open даёт те же события,
решения и экспорт; перемещённый или изменённый источник требует relink либо
явной ошибки; пользователь исправляет false positive и false negative без
потери остальных ручных правок. Export сохраняет общий ноль, длину и число
стемов, а monitor level/pan/Solo/Mute в него не попадают. Проверка проводится
минимум на tight-kit, room-heavy и cymbal/bleed-heavy сессиях; в матрице должны
быть 48 и 96 кГц. Precision, recall, повреждение атаки и слуховой результат
пишутся раздельно.

### Этап 3 — Монтаж по времени и динамике

Ценность этапа — не «нарезать аудио», а довести целую песню от найденных
событий до музыкально исправленного набора стемов. Standalone остаётся
редактором одного кита: здесь нет записи, аранжировки, плагиновых inserts и
сведения.

| Порядок | Срез | Проверяемый результат |
|---|---|---|
| 3.1 | MIDI export | Экспорт исходных либо отредактированных событий с типом, velocity и общим нулём; drag-and-drop позже отдельным UI-срезом |
| 3.2 | Источник темпа и сетка | Сначала фиксированный BPM и ручные anchors, затем оценка темпа по игре; происхождение и confidence карты сохраняются |
| 3.3 | `TimingDecision` | Observed attack не меняется; отдельно хранятся target, strength, max shift, lock и принадлежность flam/roll-кластеру |
| 3.4 | Общая карта времени | Один warp для всех микрофонов, protected zone как union атак, WSOLA только на безопасном decay; room/OH деформируются мягче close |
| 3.5 | Ручная правка монтажа | Grid overlay, before/after ghost, drag/lock/exclude, выбор по инструменту/confidence и быстрый A/B loop |
| 3.6 | Groove | Извлечение отклонений и velocity из выбранного участка, preview и применение с strength без затирания исходного исполнения |
| 3.7 | Event gain | Один коэффициент события применяется ко всем микрофонам; loudness target и strength отделены от компрессии monitor-микса |
| 3.8 | Безопасные bleed envelopes | Gain-огибающие между событиями с глубиной и audition; это baseline перед спектральным этапом 5 |

До 3.2 измеряется ручной baseline: сколько времени и критических исправлений
требует та же песня в Reaper. Продуктовый gate — инженер заканчивает полный
трек быстрее baseline без большего числа слышимых ошибок; конкретный порог
фиксируется после первых сессий, а не придумывается заранее.

**Gate этапа 3:** `strength = 0` воспроизводит вход выбранного этапа bit-for-bit;
флэмы и раскаты сохраняют внутреннюю структуру; карта времени одинакова для
всех стемов; protected attacks не растягиваются; locks и ручные anchors
переживают Save/Open и переанализ. Отдельно проверяются запись под клик,
свободный темп и плотная партия с тарелками.

### Этап 4 — DAW delivery: Reaper round-trip и ARA

Сначала Reaper round-trip через `.RPP`: проект создаётся из standalone-экспорта,
импортирует стемы, markers/regions и решения монтажа так, чтобы инженер мог
поправить спорные места привычными инструментами DAW. Это дешевле и ближе к
MVP-хосту, чем ARA, потому что RPP текстовый и не требует SDK.

| Порядок | Срез | Граница |
|---|---|---|
| 4.1 | RPP minimal | Aligned/rendered stems от общего нуля, порядок и имена дорожек, grouping, sample rate, markers/regions и ссылка на sidecar |
| 4.2 | Проверка round-trip | Автотест структуры RPP плюс smoke в текущем стабильном Reaper: пути, длина проекта, routing и повторный импорт |
| 4.3 | Native edit delivery | Splits/crossfades/stretch markers только там, где RPP выражает решение без потерь; иначе экспортируется готовый render |
| 4.4 | Workflow polish | `Open in Reaper`, portable relative paths и отчёт о том, что перенесено нативно, а что отрендерено |

RPP не становится источником правды и не импортируется обратно как полная
модель проекта. Ручная работа, сделанная уже в Reaper, принадлежит DAW; новый
экспорт создаёт новый delivery-проект и не перетирает его молча.

ARA 2 — второй канал доставки: общий документ между инстансами, рендер внутри
хоста. Адаптер поверх модели документа этапа 2, а не переписывание. Делать
тогда, когда монтаж работает и его хотят внутри DAW, а не отдельно.

Порядок ARA после доказанного спроса:

1. Проверить коммерческие условия SDK и собрать host-matrix на поддерживаемых
   версиях Reaper, Logic и Cubase/Nuendo.
2. Сделать read-adapter `ARA audio source -> beat_doc Source`, не меняя
   идентификаторы событий и decisions.
3. Сделать per-track render-adapter: каждый инстанс отдаёт только свой канал,
   все видят один документ.
4. Сравнить standalone и ARA render на одном sidecar с заданной численной
   терпимостью и пройти save/reopen в каждом заявленном хосте.

Ableton не входит в ARA gate. RPP и ARA — два независимых delivery-инкремента;
их не смешивать в одном PR или релизном обещании.

**Gate этапа 4:** RPP открывается без ручного восстановления путей и порядка
каналов, а отчёт экспорта не скрывает потери представления. ARA начинается
только после подтверждённого трения standalone round-trip; его gate —
эквивалентный документ и предсказуемый save/reopen во всех заявленных хостах.

### Этап 5 — Спектральное подавление просачивания

Отдельный исследовательский блок после того, как предыдущий workflow работает
у пользователей. Безопасная gain-огибающая этапа 3 — обязательный baseline:
спектральный метод имеет смысл только если он заметно лучше неё.

| Порядок | Срез | Решение |
|---|---|---|
| 5.1 | Evaluation corpus | Приватный набор разных комнат, тарелок, динамики и расстановок с consent и хэшами; аудио в git не попадает |
| 5.2 | Метрики | Bleed attenuation, потеря direct sound, повреждение атаки, хвоста тарелок и stereo image считаются раздельно |
| 5.3 | Offline prototypes | Маски/фильтрация по многоканальной ковариации сравниваются на одном corpus; realtime пока не нужен |
| 5.4 | Safety path | Confidence, ограничение attenuation и fallback к gain envelope при неоднозначности |
| 5.5 | Product slice | Preview одного источника, amount, bypass и ручное исключение проблемного участка; затем offline export |

**Go/no-go gate:** слепое прослушивание на нескольких китах подтверждает
выигрыш относительно gain envelope, а метрики не прячут потерю direct sound за
средним числом attenuation. Если выигрыш нестабилен, исследование остаётся
экспериментом и не усложняет основной документ или интерфейс.

### Релизная линия

Технические этапы и релизы не обязаны совпадать. ARA и спектральное подавление
не должны удерживать первую полезную версию редактора.

| Горизонт | Минимальное условие |
|---|---|
| Internal alpha | Пройден gate этапа 2; проект можно сохранить, открыть, исправить и повторно экспортировать |
| Closed beta | Есть целый timing-срез 3.1–3.5, журнал известных артефактов и измеренный Reaper baseline |
| Public v1 на macOS | Scope заморожен по beta evidence; коммерческая лицензия JUCE для закрытого бинаря, подписанный/notarized пакет, crash-safe Save, миграции проекта, отмена долгих задач, deterministic export и support matrix |
| После v1 | Windows отдельным циклом; RPP/ARA, groove/dynamics и spectral de-bleed выходят по готовности и спросу, а не все одним пакетом |

Статический плагин этапа 1 остаётся отдельным рабочим продуктом и не
превращается в урезанный режим редактора. Решение, продавать ли плагин и
редактор отдельно или bundle, принимается после beta-сессий; оно не должно
просачиваться entitlement-логикой в `beat_dsp` или `beat_doc`.

### После v1: очередь гипотез

Это не утверждённый scope. Каждая гипотеза получает discovery и свой gate до
того, как становится этапом:

- шаблон кита/сессии для повторного назначения ролей и monitor-параметров без
  переноса source-specific delays;
- batch queue песен из одной записи без превращения одного проекта в несколько
  дублей на общем таймлайне;
- QC-отчёт: клиппинг, пропавший стем, drift, нестабильная полярность и участки с
  низкой уверенностью;
- Windows после стабильной macOS-линии, отдельным PR/релизным циклом;
- дополнительные DAW adapters только по данным реальных workflow;
- обученная классификация только после замороженного corpus и доказанного
  плато классического детектора.

## 11. Открытые вопросы

- Насколько по-ударное выравнивание слышимо лучше статического на реальном материале? Проверить руками до того, как строить всю нарезку.
- Нужен ли собственный движок растяжения времени или достаточно возможностей хоста через ARA.
- Стратегия при смене состава микрофонов посреди проекта.
- Поведение при живой записи, где барабанщик двигается и расстояния плывут: пересчитывать задержки скользящим окном или считать их постоянными.
- Лицензирование ARA SDK для коммерческого продукта — уточнить условия у Celemony до этапа 4, не раньше.
- Достаточно ли инженеру круга «экспорт стемов → редактор → импорт», или ARA нужна раньше, чем этап 4. Спрашивать на реальных сессиях, не угадывать.
- Что входит в первый платный scope: статический плагин, standalone-редактор
  или bundle. Решить по beta-сессиям, не по удобству упаковки кода.
- Какой ручной baseline по времени и числу критических исправлений должен
  обогнать этап 3 на полной песне.
- Нужен ли portable project bundle с копиями источников или достаточно relink
  по fingerprint; стоимость места и авторские права на сессионное аудио
  оценивать отдельно.
- Какие форматы источников обещать публично в v1: WAV/AIFF/BWF, interleaved
  multichannel и разные длины файлов не добавлять в support matrix молча.

# 2026-09-03 — Source-centric match

## Context

PR #37 смёржен и зафиксировал проблему: source-centric diagnostic по YAN9
показывал snare bottom 0.776 мс вместо протокольных 0.281 мс, MAD 0.540 мс.
Это слишком грубо для будущей карты времени: close-пара одного источника не
должна плавать сильнее, чем сама геометрия кита.

## What

`MatchContext` теперь передаёт не только априорные задержки, но и то, какие из
них реально известны калибровке, плюс их разброс. `DetectWorker` заполняет эти
поля из `SessionProfile`.

`CrossMicMatcher` различает два режима:

- rough prior — прежняя подсказка, чтобы втащить дальний микрофон в физическое
  окно и уточнить задержку;
- trusted prior — калиброванная геометрия источника, которую нельзя заменить
  случайным более громким фронтом в широком окне.

Для trusted prior coarse search сужается до окна уточнения, а GCC residual
принимается только внутри `kMatchTrustedPriorSlackMs` или трёх разбросов
калибровки. Иначе delay остаётся калиброванным prior.

Синтетический regression добавлен в `test_cross_mic_match.cpp`: более громкий
поздний фронт в соседнем микрофоне не должен сдвинуть trusted close-пару.

## Why

Грубый поиск по огибающей полезен, когда профиль не знает пару: это честная
попытка найти наблюдение в физически допустимом окне. Но для пары, уже
померенной калибровкой, тот же поиск вреден: он превращает стабильную
геометрию в per-hit шум и особенно ломает close-пары.

Это не замена phase alignment на калибровку. GCC всё ещё может уточнить prior,
если residual мал. Большой residual считается не фазовой поправкой, а сигналом,
что корреляция/огибающая ухватилась за другой фронт.

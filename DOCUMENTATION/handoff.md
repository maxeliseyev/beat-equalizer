# Handoff (agent-based development)

Следующий человек или агент **не обязан иметь этот чат**. Всё, без чего нельзя
продолжить, живёт в git. Чат — черновик; источник правды — файлы ниже.

Протокол сжато в `AGENTS.md`. Здесь — шаблоны и «что куда».

---

## Что куда (один дом на факт)

| Факт | Куда | Не сюда |
|---|---|---|
| Где остановились, ветка, следующий шаг | `STATUS.md` (переписывать) | чат, AGENTS, конец session note как единственная копия |
| Почему выбрали A, а не B | `sessions/YYYY-MM-DD-<topic>.md` | комментарий в `.cpp`, длинный PR |
| Решение, которое всплывёт снова | `decisions/<slug>.md` | session note без ADR |
| Как устроен этап 1 / порядок PR | `plan.md` | копипаста в STATUS |
| Рамка продукта, этапы 2–4 | `drum-editor-plan.md` | код «на вырост» |
| Инварианты, которые нельзя «улучшить» | корневой `AGENTS.md` | README |
| Ветки, squash, когда `develop` | `git-workflow.md` | STATUS |
| Неочевидное в одном месте кода | короткий комментарий рядом | эссе в DOCUMENTATION |

`STATUS.md` — не лог. Лог = git + `sessions/`. Если STATUS длиннее ~80 строк,
ты пишешь историю; вынеси её в session note и укороти STATUS.

---

## Старт сессии

Пока это не сделано — не писать фичу.

1. `git status -sb`, текущая ветка, `git log -5 --oneline`.
2. Открытые PR в этот репо (если есть `gh`: `gh pr list`).
3. **`DOCUMENTATION/STATUS.md` целиком.**
4. Если STATUS ссылается на session note — прочитать её.
5. Если работаешь в зоне плана — только нужный PR из `plan.md`, не весь файл.

Если STATUS расходится с git (указана ветка, которой нет; «сделано», а файлов нет)
— **сначала починить STATUS**, потом код. Сломанный курсор = сломанная смена.

---

## Конец сессии

Даже если фича не дописана. Уйти только в чат = потерять работу для второго.

1. Код на **feature-ветке**, не на `main`. Закоммитить то, что собирается.
   Несобирающийся промежуток — либо добить, либо откатить, либо явно описать
   в STATUS.Now («не компилируется, сломан X, продолжать с файла Y»).
2. **Push ветки** (`git push -u origin HEAD`), чтобы её взял другой клон.
3. Переписать `STATUS.md` по шаблону ниже. Поля Branch / Now / Next / Resume
   обязательны.
4. Session note, если было решение, тупик или нетривиальный баг.
   Поле **Why** обязательно. Не дублировать весь STATUS — ссылка достаточна.
5. ADR, если ограничение останется после этой ветки.
6. Канон (`plan.md` / `drum-editor-plan.md` / `AGENTS.md`), если поведение
   или правило изменились — в том же изменении, не «потом в доках».

Черновик PR (draft) лучше, чем «продолжи из моего working tree».

---

## Шаблон STATUS.md

Перезаписывать целиком. Дата — день правки.

```markdown
# Status

Updated: YYYY-MM-DD
Stage: 1 (static alignment)
Plan step: PR N — <имя из plan.md>
Branch: feat/… | (none — work is on main working tree, not allowed)
PR: url | none | draft
Blockers: none | …

## Done
- слито в main / есть на ветке (явно)

## Now
- что vis-à-vis незавершено, какие файлы, что уже проверено

## Next
- один следующий шаг, не список на месяц

## Resume
1. git fetch && git checkout <branch>
2. cmake --preset debug && cmake --build --preset debug && ctest --test-dir build/debug
3. <конкретное действие: дописать тест X, открыть PR, …>

## Open
- вопросы, которые блочат Next. Пустой список = их нет.
```

## Шаблон session note

`DOCUMENTATION/sessions/YYYY-MM-DD-<topic>.md`

```markdown
# YYYY-MM-DD — <topic>

## Context
Что спровоцировало работу.

## What
Конкретные файлы / поведение. Не «порефакторил».

## Why
Альтернативы и почему отвергнуты. Обязательная секция.

## Status
STATUS.md обновлён: да. Ветка: …

## Next
Одна строка, та же, что STATUS.Next.

## Open
Известные дыры. Можно пусто.
```

Перед новым файлом — поиск по `sessions/` и `decisions/`. Дополнить существующий,
если это продолжение той же темы в тот же день.
